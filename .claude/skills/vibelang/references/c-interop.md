# C interop, both directions

C interop is not an escape hatch bolted on afterwards — it is how Vibelang inherits forty
years of libraries, and it is the only place where the guarantees stop. The spec makes that
a principle (P6): the boundary must be *syntactically visible*.

## C → Vibelang: `ext c`

```
ext c "stdio.h"
  puts : &CStr -> E! I32
end

ext c "math.h"
  fabs : F64 -> E! F64
end
```

Rules the compiler enforces:

- The string is the header, and it becomes an `#include` in the generated C.
- **`E!` is mandatory on every declaration.** The typechecker cannot know what a C function
  does, so everything from C is effectful by construction. Omitting it is `ext.pure`.
- The block closes with `end`, or it is `parse.ext`.
- An `ext` signature is a **type**, not a parameter list. See below.
- One block per header; declare as many symbols inside as you like.
- `ext c` symbols live in a namespace that is still global across modules — two modules
  declaring the same C symbol is `mod.duplicate`.

An `ext` symbol may be used as a value, not only called: `each perror xs` works, because
the compiler emits a closure wrapper for it. The same boundary type rules apply to the
wrapper, so a type that cannot cross is an error there too rather than a `cc` failure in a
generated file.

## The refinement limitation

An `ext` signature has **no binders**, so a refinement on one cannot name a parameter:

```
ext c "stdlib.h"
  malloc : (n:Size, n>0) -> E! Ptr Byte      ;; parse error — the `(name:type, refine)`
end                                          ;; parameter form is a function declaration
                                             ;; form, and is not accepted here
```

The accepted spelling is `name : type, refine` — the refinement after the whole type, where
it can only name what the call site itself names. In practice that leaves very little worth
writing. The spec draft's `(n:Size, n>0) -> E! I32` was never valid syntax; `README.md`,
spec §10.1 and `docs/remaining-work.md` all say so now.

Refinements on an `ext` are, by design, **assumed beyond the boundary and verified at the
Vibelang call sites** — they constrain your callers, they do not constrain C.

## Vibelang → C: `exp c`

```
exp c mean, total
```

One `exp c` line naming the functions to export. The compiler emits a C-ABI symbol per
name, `Module_name`, and a header:

```c
/* Ledger.h — generated by vibec */
#ifndef LEDGER_H
#define LEDGER_H

#include "vibert.h"

#ifdef __cplusplus
extern "C" {
#endif

/* mean — pre: len ts > 0   NOT VERIFIED ACROSS THE BOUNDARY */
double Ledger_mean(VbVal x0);

#ifdef __cplusplus
}
#endif
#endif
```

Two things to notice, because they are the whole design:

- The **precondition is in the header as a comment**, with an explicit warning. The
  guarantee does not cross; saying so out loud is the point.
- Scalars are unboxed into real C types (`double`, `uint64_t`, `bool`, `const char *`,
  `void` for `Unit`); **everything else stays a `VbVal`**, the runtime's uniformly tagged
  value. A record does not become a `struct` today.

`exp c` naming something undeclared is `export.unknown`.

The spec describes `own T` / `ref T` qualifiers in an exported signature, to say whether
the C caller takes ownership. Both words are reserved in the lexer and **neither is acted
on yet** — there is no `<name>_free` emission. Do not write them.

## What crosses the boundary

The compiler's actual mapping, from `codegen::c_unbox` / `c_box` / `c_type`:

| Vibelang | C, as an argument | C, as a result |
|---|---|---|
| `U8 U16 U32 U64` | `uint8_t` … `uint64_t` | same |
| `I8 I16 I32 I64` | `int8_t` … `int64_t` | same |
| `F32 F64` | `float`, `double` | same |
| `Bool` | `bool` | same |
| `Char` | `char` | same |
| `Str` | the NUL-terminated bytes | boxed back into a `Str` |
| `CStr` | `const char *` | `const char *` |
| `Ptr a` | `void *` | `void *` |
| `Unit` | — | `void` |
| `&T` | the `&` is stripped; `T` must itself cross | — |
| anything else | **`ffi.type`** | **`ffi.type`** |

`Str` and `CStr` are distinct types. Convert explicitly, in both directions, and the
conversion allocates: `to_cstr : &Str -> CStr`, `from_cstr : CStr -> Str`.

`Vec a`, records and ADTs **cannot** cross an `ext c` boundary. Marshal them yourself — a
`Ptr` plus a length, or a `CStr` — or keep the C side scalar.

## Building a library C can link

```bash
vibe build --lib mathlib.vibe
```

leaves `libmathlib.a` and `mathlib.h` next to the source, and any C project links them like
any other library. The build directory `.vibe-mathlib/` holds the generated `mathlib.c`,
plus `vibert.c` / `vibert.h` — the runtime, which is compiled into the archive.

```
mod MathLib

;; A library, not a program: no `main`, and `exp c` is the whole surface.
area (w:F64) (h:F64, w>0.0, h>0.0) : F64 = w * h

perimeter (w:F64) (h:F64) : F64 = 2.0 * (w + h)

exp c area, perimeter
```

`vibe build --emit-c f.vibe` keeps the generated C beside the output, which is the way to
see what an expression actually compiled to.

## Memory at the boundary

This is where the ownership analysis deliberately gives up, and it is worth understanding
before writing an FFI-heavy module.

- **Handing a pointer to C taints the function and every caller.** `to_cstr s` produces a
  pointer *into* `s`'s bytes; once that goes to C, neither the function nor the owner of
  the string may free it, because C keeps what it likes for as long as it likes.
- Anything that may alias is not freed at all. `vibe view --drops` counts the suppressions,
  and that count is the distance between what gets freed and what could be.
- `dup` is a deep copy — except for `CStr` and `Ptr`, which stay shallow for the same
  reason: C owns that memory and its extent is not knowable here.

## A complete, compiling example

Both directions in one file. This checks under `--prove`, formats clean, and runs.

```
mod Cbits

;; C -> Vibelang. Every signature is `E!`: the checker cannot know what C does.
;; The `#include` is emitted from the string.
ext c "math.h"
  fabs : F64 -> E! F64
end

ext c "stdio.h"
  puts : &CStr -> E! I32
end

;; Vibelang -> C. `exp c` emits a C-ABI symbol and a header entry, and the
;; precondition goes into the header as a comment that says it is not verified.
scale (x:F64) (k:F64, k>0.0) : F64 = x * k

main : E! Unit =
  d <- fabs (0.0 - 2.5) ;
  n <- puts (to_cstr "hello from C") ;
  out (fmt "{} {} {}\n" d n (scale 2.0 3.0))

exp c scale
```

```console
$ vibe run Cbits.vibe
hello from C
2.5 10 6
```

Note `0.0 - 2.5` rather than `-2.5`. That is not style: `fabs (-2.5)` is rejected as
`canon.form`, because the canonical rendering is `fabs -2.5`, which re-parses as the
subtraction `fabs - 2.5`. **A negative literal is not expressible as a bare argument** —
write the subtraction, or bind the value first.

`examples/ffi.vibe` and `tests/ext_value.vibe` are the in-repo versions; `tests/ffi_bad.vibe`
and `tests/taint_own.vibe` are the instructive failures.
