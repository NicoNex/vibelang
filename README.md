# Vibelang

Italiano: [README.it.md](README.it.md)

**A programming language that is not for you.**

Vibelang is not meant to be written by a human. It is meant to be generated by an LLM, verified by a merciless compiler, and read by you — who by now are the reviewer, not the author. If that sounds like a demotion, you have understood the project correctly.

```
mod Ledger

parse (ln:&Str) : Res Err Tx =
  ?split ',' ln
   |[s,q,p] -> ?(parse_u32 q, parse_f64 p)
                |(Some n, Some v) -> mk (dup s) n v
                |_                -> Er (Num (dup ln))
   |_       -> Er (Bad (dup ln))
```

This is not C with the sugar removed. It is the lowest-variance syntax possible for a statistical generator, paired with a type checker that lets nothing through — never a `null`, never a silent overflow, never a half-finished `match`.

---

## Why it exists

The languages we use today have been optimized for 60 years for one thing: making them pleasant for a human to write and read. Syntactic sugar, several ways of saying the same thing, implicit conventions inferred from context. All of it things an experienced programmer loves and a language model pays dearly for — every syntactic ambiguity is a fork in the road where the generator can take the wrong turn, and every error is another retry, which means more tokens, more latency, more money.

Vibelang starts from a different question than the one language design has always asked: not "how convenient is this to write", but **how many tokens does it take, in total — generation plus diagnostics plus corrections — to arrive at a correct program.** Not the brevity of the source. The real cost of the generate-compile-fix loop.

Every design choice follows from that goal:

- **exactly one valid form for every program** — the parser rejects variants instead of normalizing them, because if there are two ways to write the same thing the generator has to choose, and choosing is where errors are born;
- **no contextual rules** — the meaning of a token does not depend on where it sits in the file;
- **failure at compile time, never at runtime** — an out-of-range index, a division by zero, a non-exhaustive `match` are compile errors, not surprises in production at three in the morning;
- **structured diagnostics with a mechanically applicable `fix` field** — so the generator fixes the problem in one shot instead of retrying blindly.

Human readability is not ignored: it is a derived goal, obtained with projection tools (`vibe view --explicit`) rather than carved into the syntax itself. You look at the rendering. The generator writes the canonical form.

---

## What it guarantees (by design)

- **Zero runtime, zero GC.** Compiles to C, then to a native binary. No dependency beyond libc.
- **Pure by default.** Every function is pure until it is marked `E!`. If a function calls something effectful, it has to declare it — no silent inference.
- **Affine ownership, without lifetimes.** One owner per value, move by default, borrows with `&`. No lifetime annotations: if a value has to outlive the call, either it is owned or it is a compile error.
- **Totality.** Every function must terminate, proven with a decreasing measure — inferred where possible, explicit (`%expr`) where not.
- **Refinement types.** Preconditions and invariants in the signature itself (`n:Nat, n<=93`), discharged to an SMT solver: an unproven obligation is a compile error with a concrete counterexample, not a warning you ignore.
- **Explicit, bidirectional C boundary.** `ext c` to import any C library, `exp c` to export Vibelang functions with the C ABI. The boundary is the one place where the guarantees end, and it is syntactically visible.
- **Diagnostics designed to be read by a machine before they are read by you**, with a mechanical `fix` field whenever the repair is mechanical.

An honest note: the above is the design goal. Further down, in the *Project status* section, you will find exactly what on that list is already true today and what is still paper.

## Quickstart

Today the repository contains the **frontend** of the bootstrap compiler (lexer, parser, type checker) as a Rust library. There is no `vibe` binary yet: no `cargo install`, no executable to point at a `.vibe` file and get a native binary out. What follows under "Planned UX" is the command the project aims to offer — modeled on the Go toolchain — not what runs today.

### What you can do today

```bash
git clone <this-repo> vibelang
cd vibelang
cargo build          # builds the compiler (lexer, parser, checker, codegen)
cargo test           # runs the end-to-end tests
```

The crate is called `vibec`, and `Cargo.toml` already declares the `vibe` binary pointing at `src/main.rs`: that file does not exist yet, it is the next piece to write (see *Roadmap*).

### Planned UX (not implemented yet)

```bash
vibe new myproject          # scaffolds a .vibe module
vibe run ledger.vibe        # compiles (via C) and runs, in one shot
vibe build                  # emits the native binary
vibe check --diag=json      # type-check only, JSON diagnostics for an agent
vibe view ledger.vibe --explicit   # shows inferred types, proofs, implicit copies
```

One static binary, no build system, no configuration file. Like `go build`, not like `cargo` with its graph of feature flags.

## A Vibelang program

This is the reference program of the specification (Appendix A), the one every implementation phase has to be able to compile. It reads a CSV of transactions, validates each row, and prints total, mean and highest row — without a single explicit empty-list check in `mean` or `top`, because the compiler has already proven none is needed.

```
mod Ledger

ext c "stdio.h"
  puts : &CStr -> E! I32

type Tx  = { sku:Str, qty:U32, price:F64, qty>0, price>0.0 }
type Err = Bad Str | Num Str | Void

parse (ln:&Str) : Res Err Tx =
  ?split ',' ln
   |[s,q,p] -> ?(parse_u32 q, parse_f64 p)
                |(Some n, Some v) -> mk (dup s) n v
                |_                -> Er (Num (dup ln))
   |_       -> Er (Bad (dup ln))

mk (s:Str) (n:U32) (v:F64) : Res Err Tx =
  ?(n>0 && v>0.0)
   |True  -> Ok {sku=s, qty=n, price=v}
   |False -> Er (Bad s)

amt   (t:&Tx)      : F64 = t.price * f64 t.qty
total (ts:&Vec Tx) : F64 = ts |> map amt |> sum

mean (ts:&Vec Tx, len ts>0) : F64 = total ts / f64 (len ts)
top  (ts:&Vec Tx, len ts>0) : &Tx = ts |> max_by amt

load (p:&Str) : E! Res Err (Vec Tx) =
  txt <- read p
  ?txt |> lines |> map parse |> seq
   |Er e  -> Er e
   |Ok [] -> Er Void
   |Ok ts -> Ok ts

main : E! Unit =
  r <- load "ledger.csv"
  ?r |Er e  -> warn (show e)
     |Ok ts -> out (fmt "n={} tot={} avg={} top={}"
                        (len ts) (total &ts) (mean &ts) (top &ts).sku)

exp c mean, total
```

A note with respect to the published specification: the draft uses `u32` and `f64` as parsing conversions overloaded on the string. The bootstrap compiler does no overloading (a principle of the language, not just a limitation of the current implementation), so string parsing is `parse_u32` / `parse_f64` : `&Str -> Opt U32` / `&Str -> Opt F64`. The code above is already updated to this form.

The central point of the example: `mean` and `top` require `len ts > 0` in their signature, yet nothing in `main` checks it explicitly — because `load` has already ruled out the `Ok []` branch, and that information enters the solver's context for the `Ok ts` branch. A redundant check is not merely useless: it is an error the compiler would not let compile as "necessary", flagging it as a dead branch.

## C interoperability

The C boundary is deliberately the one place where the language's guarantees end — and it has to be visible at a glance, not buried inside a generated binding.

**Importing a C library:**

```
ext c "sqlite3.h" link "sqlite3"
  sqlite3_open : &CStr -> E! I32
  sqlite3_exec : (n:Size, n>0) -> E! I32
```

`link` carries the library name to pass to the linker; `pkg` does the same with a `pkg-config` package. Every `ext c` signature is mandatorily `E!`: the typechecker has no way of knowing what a C function does, so it assumes the worst case by construction. Refinements on an `ext` signature are assumed, not proven — checked at the Vibelang call sites, not beyond the boundary.

**Exporting to C:**

```
exp c mean, total
```

This generates symbols with the C ABI plus a header, with only two possible ownership qualifiers in the exported signature: `own T` (the C caller takes ownership, and `<name>_free` is exported as well) and `ref T` (a borrow valid only for the duration of the call). Preconditions end up in the header as a comment, with an explicit warning that beyond the boundary they are not verified:

```c
/* mean — pre: len(ts) > 0   NOT VERIFIED ACROSS THE BOUNDARY */
double Ledger_mean(const Ledger_Vec_Tx *ts);
```

## Diagnostics

The compiler emits readable prose by default. With `--diag=struct` (or `--diag=json`, for an agent) it emits the same content in term form, with a stable semantic path instead of a line number, and — where the repair is mechanical — a `fix` field applicable without human intervention:

```
✗ Ledger.mean.body/2 div0 ⊨ len ts == 0
  at: ledger.vibe:19:34
  msg: division may fail: divisor could be zero
  fix: Ledger.mean.sig += len ts > 0
```

```
✗ Ledger.parse.match nonexhaustive ⊨ missing [_, _]
  at: ledger.vibe:9:3
  msg: match is not exhaustive
  fix: add arm |_ -> Er (Bad (dup ln))
```

By the metric of §0 of the specification, the `fix` field is the highest-yield point of the entire design: it closes the correction loop in a single diagnostic instead of a blind retry. A refinement failure always carries a concrete counterexample from the SMT model — never a generic warning left to you to interpret.

## Project status

**Pre-alpha.** There is no `vibe` binary yet, no C code emission, not a single `.vibe` compiled end to end. What follows is the real state of the library in `src/`, not a goal dressed up as a changelog.

**Implemented:**

- complete lexer and parser for the grammar of the specification, including the canonicity rules (P1): 2-space indentation, no redundant parentheses, no multiple blank lines — the parser *rejects*, it does not normalize;
- AST and name resolution;
- type checker with Hindley–Milner inference;
- ADTs with payloads, records with fields, pattern matching with exhaustiveness checking;
- effect propagation (`E!`): a function that calls an effectful one has to declare itself as such, with no silent inference;
- refinements in the signature type-checked as boolean expressions in the scope of the parameters (the *syntactic* part of §7 of the specification);
- parsing of `ext c` with `link`/`pkg` and of `exp c`;
- structured diagnostics (`--diag=struct` / `--diag=json`) with semantic path, witness and mechanical `fix` field where applicable.

**Not implemented yet:**

- the `vibe` binary itself and its CLI (`run`, `build`, `check`, `new`, `view`, `patch`);
- C emission and any form of compilation to a native binary;
- the borrow checker and in-place reuse;
- termination checking (measure inference, verification of `%`);
- actually discharging refinement obligations to an SMT solver — today they are type-checked as booleans, not proven;
- the minimal runtime library (arenas, `Vec`, `Str`/`CStr` conversions);
- any module system beyond a single file.

If a section above describes a behavior and you do not see it in this list, it is design, not functionality.

## Roadmap

The phases mirror those of the specification (§15), arranged to surface the real risks early instead of deferring them.

| Phase | Content | Status |
|---|---|---|
| 0 | Hypothesis validation: 50 tasks generated in Rust/Haskell vs. mocked Vibelang syntax, measuring tokens to a correct program | not tracked in this repo |
| 1 | Frontend — lexer, parser with canonicity checking, AST, name resolution | **done** |
| 2 | Typechecker — HM inference, ADTs, exhaustiveness, effects | **done** (refinements type-checked, not yet proven) |
| 3 | C emission — no ownership, allocates and never frees, to validate type mapping, FFI and the minimal runtime | not started |
| 4 | Ownership — borrow checker, in-place reuse, escape analysis | not started |
| 5 | Totality — measure inference, termination checking | not started |
| 6 | Refinement — obligation generation, Z3 integration, counterexamples, structured diagnostics | partially: the syntax and the type-checking of refinements exist, the solver is missing |
| 7 | Tooling — views (`view`), structured patches (`patch`), agent-facing surface | not started |

Phases 1–3 are the ones that make the language usable for writing and compiling real programs; this repo is halfway through phase 2. Phases 4–6 are independent of each other and can proceed in a different order.
